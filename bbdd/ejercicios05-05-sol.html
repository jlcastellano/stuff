Ejercicios de Transacciones SQL

Ejercicio 1: Identificación de Problemas de Concurrencia

En un sistema bancario, dos transacciones se ejecutan simultáneamente:

-- Transacción 1 START TRANSACTION; SELECT saldo FROM cuentas WHERE id = 100; -- (saldo = 1000) -- espera 5 segundos SELECT saldo FROM cuentas WHERE id = 100; COMMIT; -- Transacción 2 (ejecutada durante la espera) START TRANSACTION; UPDATE cuentas SET saldo = 800 WHERE id = 100; COMMIT;

¿Qué problema de concurrencia se está produciendo en este escenario?

Este es un caso clásico de una lectura no repetible (non-repeatable read).

La primera lectura de la Transacción 1 mostrará 1000, pero la segunda lectura mostrará 800, porque la Transacción 2 ha modificado y confirmado el valor entre las dos lecturas.

Para prevenir este problema, se debería usar un nivel de aislamiento REPEATABLE READ o superior.

Ejercicio 2: Diseño de Transacción Segura

Diseña una transacción para transferir dinero entre dos cuentas que sea:

  • Atómica
  • Consistente (el saldo no puede ser negativo)
  • Protegida contra lecturas sucias
SET TRANSACTION ISOLATION LEVEL READ COMMITTED; START TRANSACTION; -- Verificar y bloquear cuenta origen SELECT @saldo := saldo FROM cuentas WHERE id = 1 FOR UPDATE; IF @saldo >= 500 THEN -- Debitar cuenta origen UPDATE cuentas SET saldo = saldo - 500 WHERE id = 1; -- Acreditar cuenta destino UPDATE cuentas SET saldo = saldo + 500 WHERE id = 2; COMMIT; ELSE ROLLBACK; SELECT 'Saldo insuficiente' AS mensaje; END IF;

Ejercicio 3: Corrección de Código

El siguiente código tiene un problema. Identifícalo y corrígelo:

START TRANSACTION; UPDATE inventario SET stock = stock - 1 WHERE producto_id = 100; INSERT INTO ventas (producto_id, cantidad) VALUES (100, 1); IF stock < 0 THEN ROLLBACK; ELSE COMMIT; END IF;

El problema es que se está verificando el stock después de actualizarlo. La solución correcta sería:

START TRANSACTION; -- Primero verificar el stock SELECT @stock := stock FROM inventario WHERE producto_id = 100 FOR UPDATE; IF @stock > 0 THEN UPDATE inventario SET stock = stock - 1 WHERE producto_id = 100; INSERT INTO ventas (producto_id, cantidad) VALUES (100, 1); COMMIT; ELSE ROLLBACK; SELECT 'Stock insuficiente' AS mensaje; END IF;

Ejercicio 4: Niveles de Aislamiento

Para cada uno de los siguientes escenarios, elige el nivel de aislamiento más apropiado (el menos restrictivo que resuelva el problema):

  1. Generación de reportes estadísticos que pueden tolerar algunas inconsistencias
  2. Proceso de pago que requiere saldo exacto
  3. Actualización de inventario que debe prevenir ventas duplicadas
  4. Conteo de registros que debe ser consistente durante toda la transacción
  1. READ UNCOMMITTED - Suficiente para reportes no críticos
  2. READ COMMITTED - Previene lecturas sucias de saldos no confirmados
  3. SERIALIZABLE - Necesario para prevenir inserciones fantasma en el inventario
  4. REPEATABLE READ - Asegura que los conteos sean consistentes

Ejercicio 5: Uso de Savepoints

Diseña una transacción que use savepoints para un proceso de compra con múltiples productos, donde si falla un producto, los anteriores se mantienen:

START TRANSACTION; INSERT INTO pedidos (cliente_id) VALUES (1); SET @pedido_id = LAST_INSERT_ID(); -- Primer producto SAVEPOINT producto1; UPDATE inventario SET stock = stock - 1 WHERE id = 100; INSERT INTO detalles_pedido VALUES (@pedido_id, 100, 1); -- Segundo producto SAVEPOINT producto2; UPDATE inventario SET stock = stock - 1 WHERE id = 101; IF ROW_COUNT() = 0 THEN ROLLBACK TO producto2; -- Continuar con el resto del pedido ELSE INSERT INTO detalles_pedido VALUES (@pedido_id, 101, 1); END IF; COMMIT;

Ejercicio 6: Detección de Pérdida de Actualizaciones

Analiza el siguiente escenario y propón una solución:

-- Usuario 1 START TRANSACTION; SELECT precio FROM productos WHERE id = 1; -- precio = 100 -- Calcula nuevo precio con 10% de incremento UPDATE productos SET precio = 110 WHERE id = 1; COMMIT; -- Usuario 2 (simultáneamente) START TRANSACTION; SELECT precio FROM productos WHERE id = 1; -- precio = 100 -- Calcula nuevo precio con 20% de descuento UPDATE productos SET precio = 80 WHERE id = 1; COMMIT;

El problema es una pérdida de actualización (lost update). La solución es usar SELECT FOR UPDATE:

-- Usuario 1 START TRANSACTION; SELECT precio FROM productos WHERE id = 1 FOR UPDATE; -- Calcula nuevo precio con 10% de incremento UPDATE productos SET precio = 110 WHERE id = 1; COMMIT; -- Usuario 2 esperará hasta que la primera transacción termine

Ejercicio 7: Deadlock Prevention

Identifica el potencial deadlock en este código y corrígelo:

-- Transacción 1 START TRANSACTION; UPDATE cuentas SET saldo = saldo - 100 WHERE id = 1; UPDATE cuentas SET saldo = saldo + 100 WHERE id = 2; COMMIT; -- Transacción 2 (simultánea) START TRANSACTION; UPDATE cuentas SET saldo = saldo - 50 WHERE id = 2; UPDATE cuentas SET saldo = saldo + 50 WHERE id = 1; COMMIT;

La solución es ordenar las actualizaciones siempre en el mismo orden:

-- Transacción 1 START TRANSACTION; UPDATE cuentas SET saldo = saldo - 100 WHERE id = 1; UPDATE cuentas SET saldo = saldo + 100 WHERE id = 2; COMMIT; -- Transacción 2 START TRANSACTION; UPDATE cuentas SET saldo = saldo - 50 WHERE id = 1; UPDATE cuentas SET saldo = saldo + 50 WHERE id = 2; COMMIT;

Mejora esta transacción agregando gestión de errores apropiada:

START TRANSACTION; INSERT INTO pedidos VALUES (NULL, 1, NOW()); INSERT INTO detalles_pedido VALUES (LAST_INSERT_ID(), 100, 2); UPDATE inventario SET stock = stock - 2 WHERE producto_id = 100; COMMIT;
